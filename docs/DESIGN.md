# rust-android-kb — design

Цель: движок исправления/автодополнения для экранной клавиатуры (Android IME,
позже десктоп). Требования: **офлайн, минимум RAM, ноль пересчёта при старте,
несколько языков (RU ЙЦУКЕН, EN QWERTY, DE QWERTZ, FR AZERTY, ES, PT-BR),
взвешенная модель ошибок по геометрии клавиатуры.** Русско-английский словарь —
~3,5 млн форм (FST ~7,6 МБ), словари остальных языков — 0,4–0,7 млн форм
(1,9–3,4 МБ).

Документ описывает три части: структуры данных, модель ошибок и мобильную
архитектуру. Источники — в конце.

## 1. Структура данных индекса

**Решение: `fst::Map` (слово → u64 с квантованной лог-частотой), mmap, поиск —
собственный взвешенный обход (DFS с отсечением) по `fst::raw::Fst`.**

Почему:
- `fst` уже в зависимостях, mmap-friendly, префиксно-суффиксное сжатие
  (3,5 млн форм → 7,6 МБ), 0 heap для индекса — словарь лежит чистыми файловыми
  страницами, которые система может вытеснить в любой момент.
- Встроенный `fst::automaton::Levenshtein` даёт только **равномерное** расстояние ≤2
  без весов — нам недостаточно. Поэтому свой обход графа с матрицей стоимостей.
- Отклонено: **SymSpell** (RAM в сотни МБ–ГБ, не mmap), **BK-деревья**
  (резидентны, требуют метрику — наши пространственные веса её нарушают),
  **rustfst** (тяжёлый WFST, избыточен), **MARISA** (меньше на диске, но теряем
  удобный API узлов и значения-частоты — держим как запасную оптимизацию).

Персистентность: `index-builder` (десктоп-утилита) собирает блоб **один раз**,
формат little-endian (все таргеты LE), с заголовком `magic + version`. Рантайм
только mmap-ит. Пользовательские (доученные) слова — отдельный маленький оверлей,
большой блоб иммутабелен.

## 2. Модель ошибок (noisy channel)

`ŵ = argmin_w [ w_lm·(−log P(w)) + w_ch·EditCost(x, w) ]`

- **P(w)** — приоритет по частоте слова (внешний частотный список; при отсутствии —
  равномерный, ранжируем только по EditCost). Хранится в значении FST как
  квантованная `−log`-частота.
- **Поиск** — DFS по FST с взвешенной Damerau-Levenshtein строкой на узел.
  Ветка отсекается, когда минимум строки (допустимая нижняя оценка) превышает
  бюджет; дети обходятся в порядке близости к вводимому символу (ныряем вдоль
  искомого слова, не голодаем на глубоких словах). **Адаптивное расширение
  бюджета**: стартуем с малого порога, и пока близких кандидатов мало —
  поднимаем порог и ищем снова, пересматривая отсечённые ранее ветки. Так слова
  с большим числом опечаток всплывают только когда ближе ничего нет, а частый
  случай остаётся быстрым. Матрица стоимостей замен предвычислена (без хэшей в
  горячем пути). Текущие замеры — в конце §2.
- **EditCost** — минимальная взвешенная Damerau-Levenshtein по операциям:
  - `match` = 0
  - `substitute a→b` = `d(a,b)² / (2σ²) + base_sub` — геометрия (см. §3); поверх —
    минимум с «негеометрическими» заменами: фонетические пары (о/а, е/и, е/я, и/ы,
    е/э, о/ё, ю/у, б/п, в/ф, г/к, д/т, ж/ш, з/с; в английском a/e, e/i, i/y, c/k,
    c/s, s/z) = `C_phon`; е→ё = `C_yo` (почти бесплатно), ё→е = `C_yo_rev`
    (набрать ё случайно трудно); ь↔ъ = `C_hard_soft`
  - `insert` (лишняя буква) = `C_ins`, но дешевле с учётом соседей во вводе:
    повтор предыдущей (дребезг) `C_ins_repeat`, соседняя по клавиатуре с
    соседней набранной (нажал две клавиши) `C_ins_neighbor`, лишний ь/ъ `C_ins_sign`
  - `delete` (пропущенная буква) = `C_del`; пропуск удвоенной (`коректный`)
    `C_del_double`, пропуск ь/ъ `C_del_sign`, апострофа/дефиса `C_del_punct`
  - `transpose ab→ba` = `C_trans`
- Каждая стоимость = `−log P` операции → размерно совместимо с приоритетом.
  У каждого события свой вес, все веса настраиваются по имени: `Config::set_param`, в CLI — `KB_SET="c_del=3.5,..."`.
- Все таблицы (замены, вставки/пропуски, соседство, φ) строятся **один раз** при
  создании движка / смене раскладки (`Engine::set_config`); на запрос — только
  таблица `стоимость[буква][позиция ввода]` (≤ 62×32), горячий цикл = чтения массива.
- **Отсечение:** ветка режется, если `w_ch·min(row)` > бюджета или
  `w_ch·min(row) + w_lm·out_acc + штраф гипотезы` > k-й лучший итог, где
  `out_acc` — накопленный выход FST = нижняя граница `−log P` для всего поддерева.

### Веса (nats), подобраны `tools/eval.py` на seed 1, проверены на seed 2

## 3. Геометрия клавиатуры → стоимость замены

Каждая клавиша = центр в единицах ширины клавиши на **staggered** сетке:
`x = col + row_offset`, `y = row`. Расстояние — евклидово между центрами.
`C_sub` из гауссовой модели касания (как LatinIME/GBoard): вероятность попасть в
клавишу j целясь в i ∝ `exp(−d²/2σ²)` ⇒ `C_sub = d²/(2σ²) + base_sub`.

Геометрия задаётся профилем (`Config::profile`):
- **Desktop** — квадратные клавиши, ANSI-стаггер рядов `top 0.5, home 0.75,
  bottom 1.25`; QWERTY и ЙЦУКЕН (12 клавиш в верхнем ряду) на **идентичных
  физических позициях** — ключ к §4; ё — на клавише `` ` ``.
- **Phone** (как Gboard) — клавиши выше, чем шире (высота ряда 1,35 ширины
  QWERTY-клавиши), QWERTY 10 клавиш в ряду со сдвигами `0, 0.5, 1.5`, ЙЦУКЕН
  11 более узких клавиш со сдвигами `0, 0, 1`; ё и ъ — долгим нажатием на е и ь.

Координаты — в `keyboard.rs` (латинская раскладка задаётся языком: QWERTY,
QWERTZ, AZERTY, с ñ, с ç). На телефоне клавиатура передаёт ещё и сами точки
касаний: стоимость замены считается от места, куда попал палец.

Буква без диакритики вместо буквы с ней (`e` вместо `é`, `n` вместо `ñ`,
`u` вместо `ü`) почти бесплатна (`c_accent` = 0,2, как `е`→`ё`); выбранная
долгим нажатием буква с диакритикой вместо другой — дорого (`c_accent_reverse`).

## 4. Кросс-раскладка (`ghbdtn` → `привет`)

Систематическая ошибка (правильные физические клавиши, не та активная раскладка) —
отдельная гипотеза, а не ослабление весов. Биекция φ по физической позиции
(Q↔Й, W↔Ц, …). Для токена x пробуем: x как есть **и** φ(x), гоняем noisy-channel в
словаре каждой раскладки, берём глобально лучший по Cost + `layout_switch`.
Композируется с моделью правки (можно чинить даже опечатанное слово в чужой раскладке).
Бюджет гипотезы ограничен `layout_max_cost` (≈ одна опечатка, без расширения):
ошибка систематическая, слово набрано целиком. Включена только в профиле Desktop —
на телефоне клавиши подписаны, и гипотеза давала лишь ложные срабатывания (`ещо`→`to`).

## 4б. Домашний ряд / однострочная клавиатура

Если все набранные клавиши из домашнего ряда, пробуем гипотезу «руки не сходили с
домашнего ряда»: каждая клавиша означает любую клавишу своего пальца (Desktop,
слепая печать: `ааоаааоаыа` → `каракатица`) или своей колонки (Phone — задел под
режим как у Minuum, где три ряда сжаты в один и важна только координата x).
Цена «своего пальца» `C_home_finger`, штраф гипотезы `home_row_penalty`, свой
лимит узлов.

## 5. Мобильная архитектура

- **Максимум логики на Rust.** Android требует Java-класс `InputMethodService` —
  он тонкий (`android/java/…`): пересылает касания и события
  редактора в Rust, применяет текстовые операции (`commit`/`composing`/`delete`)
  и рисует готовый список отрисовки штатным `Canvas`. Всё остальное — раскладки,
  попадание касания в клавишу, roll-over, долгое нажатие, автоповтор ⌫,
  составляемое слово, автоисправление на пробел и его откат по ⌫, полоса
  подсказок, автозаглавные, выбор цветов и размеров — в `crates/android`
  (`ime.rs`, `layout.rs`), чистый Rust с тестами на десктопе.
- **Связка:** ручной JNI (крейт `jni`, `crates/android/src/lib.rs`), а не UniFFI —
  UniFFI для Kotlin тянет JNA (лишняя библиотека и память) ради API из десятка
  функций. Каждая точка входа ловит панику (`catch_unwind`, release собирается
  с unwind): баг превращается в no-op, а не в падение клавиатуры.
- **Сборка APK без Gradle** (`android/build.sh`): `cargo-ndk` → `javac` → `d8` →
  `aapt2` → `zipalign -P 16` → `apksigner`. Секунды и мало памяти; окружение —
  `nix develop` (flake: SDK/NDK из nixpkgs, Rust с `aarch64-linux-android` из
  fenix), в CI — GitHub Actions (`.github/workflows/ci.yml`).
- **Словарь:** `data/lexicon.tsv` → `dict.fst` в assets APK (без сжатия); при первом
  запуске копируется в `filesDir` и mmap-ится. Замер показал, что при наборе
  через ~10 нажатий резидентен весь файл, а `MADV_RANDOM` ничего не меняет —
  поэтому память = размер файла, экономим размером словаря.
- **Бюджет:** ≤30 МБ PSS / ≤15 МБ heap. Движок: ~0,3 МБ heap + словари (чистые
  файловые страницы: для RU+EN ~20 МБ вместе с контекстом); основная статья —
  сам процесс ART + UI. Замер на телефоне: PSS клавиатуры ~43 МБ против
  ~83 МБ у HeliBoard и ~178 МБ у Gboard.
- Референсы IME-обвязки: HeliBoard, OpenBoard (форки LatinIME), FlorisBoard.

## 6. Статус и план

Сделано: FST-ядро, геометрия (desktop/phone), фонетика/ё/ь, умные вставки и
пропуски, гипотезы (кросс-раскладка, домашний ряд), автодополнение, бенчмарк,
Android IME (Rust + тонкий Java-слой), сборка без Gradle, CI; точки касаний,
удержание/скольжение/roll-over; ошибки пробела, запятой и точки (склейка и
разбиение); контекст — пары слов (Tatoeba + веб) и модель окончаний, окно из
двух слов (перечитать предыдущее слово по следующему); однострочный режим;
калибровка хвата (дуги пальцев, фраза каждой рукой, наклон) с индикатором и
поправкой касаний; набор свайпом; правила на следующее слово для слов, которые
путаются одной клавишей (docs/rules-format.md); языковые пакеты DE/FR/ES/PT;
темы и перевод интерфейса; раскладка по области большого пальца;
согласование и падеж после предлога; темп пальца вдоль свайпа; эмодзи и
буфер обмена.

Дальше: одна структура для слов и их грамматики (сейчас ключи хранятся
дважды: в словаре и в модели контекста), разборы и формы для слов вне
словаря; правила, обученные внешним обучателем (docs/rules-format.md); псевдокурсор для одной руки
(площадка под пальцем рисует свайп); поиск эмодзи по названию и оттенки кожи;
триграммы для предсказания; словари прямо из APK без копирования; сброс
страниц словаря, когда клавиатура скрыта (`MADV_DONTNEED`); версия для ПК
(лаунчер, поиск файлов).

### Грамматика фразы (`crates/core/src/gram.rs`)

У каждого слова словаря — набор всех его разборов (pymorphy3, все, даже
редкие: `такой` — чаще женский род, но и мужской; `его` — и родительный), 1873
разных наборов; номер набора лежит в том же значении `0, 3, слово`, что и
класс (биты выше 16-го), разборы набора — под `0, 9, набор, i` (граммемы
битами). Обрезанные по 15% классы для пар тегов для этого не годятся:
правильное слово получало штраф за «несуществующий» разбор.

От слова назад: прилагательные и причастия (и «и»/«или» между ними) до
предлога — слово должно стоять в падеже, которым управляет предлог, и
согласоваться с ними (падеж, число, род в единственном); без предлога — только
согласование. Местоимение-подлежащее перед глаголом: несогласованный глагол
(«она сказал», «я иди») штрафуется. Разборы берутся все, без порога
вероятности: у pymorphy «ним» — 0,8% творительный, «все» — 0,8% прилагательное.
Слово, которое может быть и не прилагательным («это», «его», «все»),
согласования не требует («это моя книга»).
Грамматика только запрещает: неподходящее дороже на `w_phrase` = 1 нат (2 —
уже хуже, `tools/eval_phrase.py`), подходящее ничего не получает — иначе
после «один» предлог «из» проигрывал согласованным существительным. Соседние
прилагательные одной группы согласуются между собой, иначе это две группы
(«к этому никакого отношения»). В предсказании следующего слова (кандидаты —
из пар слов) запрещённые формы просто выбрасываются: «к большим» → «деньгам»,
не «успехом».

Сколько это стоит (3,19 млн русских словоформ, отдельный FST): одни ключи —
1,8 МБ (0,6 байта на форму); с номером класса — 2,6 МБ; с номером набора всех
разборов (часть речи, падеж, число, род, лицо, время — склонение и спряжение)
— 2,5 МБ; с обоими — 3,6 МБ. Минимальный автомат сам сливает хвосты слов с
одинаковым окончанием и одинаковой грамматикой — выводит правила «окончание →
разборы» и точно хранит исключения. Для сравнения, правила по последним
буквам (большинство для окончания) оставляют исключений: 4 буквы — 48 тыс.
правил и 548 тыс. исключений (17% форм, 27% текста: частые слова самые
неправильные), 6 букв — 444 тыс. правил и 209 тыс. исключений (7% и 8%).

### Выученные рамки управления (`tools/build_frames.py`)

Жёсткие запреты заменены весами из текста (идея взвешенной грамматики
ограничений, WCDG). По Tatoeba (без отложенных) и вебу
Leipzig каждое слово фразы читается так же, как клавиатура его читает (назад
через прилагательные и «и» к управляющему слову — предлогу, глаголу,
существительному — мимо наречий и частиц), и для каждого управляющего слова,
встреченного ≥ 100 раз, считается, во сколько раз чаще среднего дальше идёт
именная группа в каждом падеже или что-то другое: ln(P(исход | слово) /
P(исход)), сглаженно к среднему. Хранятся только те, что что-то говорят
(|log-отношение| ≥ 0,3 где-нибудь): 11 тыс. из 313 тыс., байт на исход,
`0, 11, слово` в модели контекста; после прилагательных — `0, 12`.
Корпус сам нашёл: «к», «по» — дательный (+2,7), «с», «между», «над» —
творительный (+2,6…2,8), «из», «у», «без», «для» — родительный (+1,4…1,6),
«о», «при» — предложный (+2,1), «помочь» — дательный (+2,4), «видел» —
винительный (+0,9); после прилагательного несогласованное −2,7, не-именное
−1,1, согласованное +0,4.

Чтобы не считать дважды: для слова сразу после управляющего модель пар уже
знает, что там идёт, — рамка встаёт на место запасной оценки по классам
(точнее её: у класса предлога нет самого предлога); сверху прибавляется
только то, чего пары не видят: управляющее слово через прилагательные («из
старого дома») и несогласование с ними. Через прилагательные уже ясно, что
идёт именная группа, поэтому падежи рамки берутся условно — среди именных
исходов (после «можешь» почти всегда инфинитив, но «можешь весь день» —
винительный), а управляющим через прилагательные считается только предлог
или глагол («мне свой номер» — управляет глагол раньше; «Мария высокого
мнения» — не существительное). Слово с несколькими разборами («казни» —
существительное и глагол) весит по лучшему. Подходящее получает прибавку,
редкое законное — только своё log-отношение, не запрет; в предсказании
отбрасывается всё, что фраза весит ниже −1 ната. Цена — обороты вроде «с
большой буквы»: «с» тянет к творительному (такие обороты требуют трёх слов).

Стек ожиданий: когда перед словом стоит именная группа, а перед ней в той же
клаузе глагол («дал книгу [другу]», «помог ему [встать]»), слово весит рамка
клаузы глагола — что идёт после именной группы в его клаузе, против любой
клаузы (`%глагол` в `frames.tsv`, `0, 16, глагол`; 1113 глаголов, встреченных
≥ 100 раз, из 616 тыс. таких мест): после «дал …» — винительный +0,84,
дательный +0,61, именительный +0,97 («дал ему отец»); после «помог …» —
инфинитив +2,4; после «сказал …» — инфинитив +1,5. Пары слов глагола не видят
(он в двух и больше словах назад). Таблица «какой падеж после какого» внутри
клаузы не берётся: её уже знают классы соседних слов. Набор с шумом не
меняется (93,35 → 93,33%: там грамматика говорит в основном после предлогов);
«он дал книгу другк» → «другу», «он помог ему встаьь» → «встать».

Замеры (`tools/eval_phrase.py`): набор с шумом 93,29 → 93,35% слов (рамка
соседнего слова в модели контекста; через прилагательные — в пределах
шума при любом весе), 0 лишних исправлений; предсказание следующего слова
там, где грамматика участвует, top-1 10,1 → 10,2% (3000 предложений), в
остальных местах без изменений. `w_phrase` = 0,5.

Свайп целыми предложениями (`tools/eval_phrase.py --swipe 0.3`: `typetext`
рисует каждое слово — палец садится на первую букву, углы уходят на σ = 0,3
клавиши, темп с торможением на поворотах): без грамматики и классов 93,46%
слов, с рамкой соседнего слова 93,63%, с грамматикой через прилагательные
93,64% (среди слов, о которых грамматика что-то говорит: 92,88 → 93,22%).
Ошибки свайпа (1500 предложений): другое слово — 62% («кошка» → «крошка»,
«делаете» → «желаете»: нужен смысл), та же лемма в другой форме — 24%
(«понравился» → «понравиться», «турнира» → «турнир»), короткие частые слова,
вытесненные редкими, — 13% («мне» → «инк», «три» → «торт»). Последнее — не
частота против формы (ослабление формы для коротких жестов ничего не дало), а
перебор: первая и последняя буквы должны лежать у концов пути, в пределах 4
из 40 точек, — у короткого жеста это четверть клавиши, меньше, чем сдвигает
сглаживание, и «мне» вовсе не попадало в кандидаты. Теперь допуск — не меньше
1 клавиши: «мне» 145 → 170 из 200, свайп по предложениям 93,64 → 94,53% слов
(предложений с неверным числом слов 13 → 4; цена — чуть больше путаницы
длины формы: «запрыгал» → «запрыгало»).

Небрежный свайп. Диагностика по словам предложений (`swipesim` с
`SENTENCES`: слово рисуется, читается с контекстом, как в клавиатуре):
правильное слово первым в 93,1%, на 2–3 месте в 4,5%, не найдено в 1,9%.
Постоянные веса дают размен (меньше веры геометрии — лучше небрежным, хуже
аккуратным), поэтому небрежность оценивается у каждого жеста: если даже
лучшее слово лежит от пути дальше `gesture_trust` = 0,3 клавиши, геометрия
весит меньше в квадрате этого отношения (частота и контекст — больше;
ничего не запоминается). И если ничто не легло ближе 0,6 клавиши, путь
читается ещё раз с радиусом 1,5 клавиши вместо 1,1 — для слов, чьи углы
ушли дальше. Свайп по предложениям, весь конвейер: σ = 0,3 — 94,53 → 95,33%
слов; σ = 0,4 — 90,6%; σ = 0,2 — 97,5% (как было). По словам: σ = 0,35 —
77,1 → 80,3%, σ = 0,5 — 46,1 → 59,9% (до 1,35 мс на небрежный жест).

### Запятые (`tools/build_commas.py`)

По Tatoeba и вебу Leipzig: как часто между двумя соседними словами стоит
запятая (база 9,2%) — по слову после («но» +4,0 в логарифме шансов,
«которая» +3,7, «а», «чтобы» +2,6, «что» +1,5), по слову до («думаю»,
«например» +2,0…2,2) и по паре, когда она говорит больше двух слов порознь
(«потому что» — без запятой); 58 тыс. записей, байтом под `0, 15`. Шансы
пары — её собственные или база плюс свидетельства обоих слов. На отложенных
предложениях Tatoeba (6703 запятые): при уверенности ≥ 0,85 верны 98,5%
поставленных, найдена половина запятых; ≥ 0,95 — 99,6% и 30%; ≥ 0,5 — 91% и
69%. Клавиатура ставит запятую сама при ≥ 0,9, когда слово ушло пробелом
после другого слова (только пробел между ними): «я думаю что» → «я думаю,
что»; ⌫ сразу после убирает её, и для этой пары в этом поле она больше не
ставится. Выключается настройкой. Дальше — варианты для двусмысленного
(«казнить нельзя помиловать») в полосе после конца предложения.

### Классы смысла (`tools/build_topics.py`)

О чём предложение: 20 тыс. частых содержательных лемм (существительные,
глаголы, прилагательные, наречия) по Tatoeba и вебу Leipzig — с какими из
2 тыс. опорных лемм они встречаются в одном предложении (положительный PMI),
сжато рандомизированным SVD до 64 чисел на лемму и разбито сферическим
k-means на 512 классов: «кошка» — собака, животное, кот, лошадь, мышь;
«хлеб» — есть, яблоко, пирог, торт; «поезд» — машина, автобус, вокзал,
такси; «врач» — пациент, больница, лекарство. Все формы леммы получают её
класс (411 тыс. словоформ, `0, 13, слово` в модели контекста), пары классов,
встречающиеся в предложении заметно чаще или реже случайного (|PMI| ≥ 0,3,
≥ 20 раз; 41 тыс. пар из 125 тыс.), — байтом под `0, 14, класс, класс`.
Кандидат получает `w_topic` × среднее PMI своего класса с классами слов
предложения до курсора (≤ 12 слов, до точки).

Размер: 0,6 МБ карта слов + 0,3 МБ пары. В значении словаря рядом с
частотой класс стоил 3,1 МБ: он одинаков у всех форм леммы, и отдельно
поднимается на основу — окончания общие, а смешанный с частотой формы
дробит хвосты. Точность на свайпе по предложениям Tatoeba: 94,53 → 94,58%
при `w_topic` = 0,5 (1 — 94,56%, 2 — хуже: 94,31%); среднее, максимум и
сумма положительных связей дают одно и то же — в коротком предложении до
курсора обычно одно содержательное слово. Чинит «рыба гниёт с головы», «на
стол», «на выходные»; в длинных текстах сигнал должен быть сильнее.

### Одна структура для слов, частоты и грамматики (`crates/core/src/dict.rs`)

Значение слова в `dict.fst`: частота (−ln P × 1000) шагами по 0,05 ната, под
ней — номер грамматики (пара «класс + набор разборов», 3143 пары, 12 бит,
частые пары — маленькие номера); что значит номер — в модели контекста под
`0, 10, номер`. Формат записан в поле типа заголовка FST (старые словари —
тип 0). Частота сверху — поэтому выход, накопленный по пути к узлу (минимум
значений под ним), остаётся нижней границей частоты для отсечения поиска.

| что | МБ |
|---|---|
| словарь, частоты ×1000 (было) + модель контекста со своей копией слов | 7,6 + 13,0 = 20,6 |
| частоты шагами 0,05 ната (исправления те же: 77,1% top-1 и при шаге 0,2) | 6,3 + 13,0 = 19,3 |
| грамматика в словаре 24 битами (класс и набор как есть) | 11,4 + 9,5 = 20,9 |
| грамматика в словаре плотным номером, 12 бит | **9,0 + 9,5 = 18,5** |

Весь набор (`tools/eval_typing.py`, 600 предложений) — те же 95,5% слов и
0/1 изменённых; APK 53,6 → 49,4 МБ. Почему грамматика в одной структуре с
частотой дороже, чем одна (слова — 2,5 МБ, слова с грамматикой — 3,4, слова с
частотой — 6,3, всё вместе — 9,0): автомат сливает хвосты с одинаковыми
остатками значений, грамматика зависит от окончания (хвосты общие), а частота
— свойство формы: у «-ила» в «любила» и «носила» разные остатки. Ширина
выходов в узле FST — по самому большому, поэтому номер плотный.

Разложение частоты (`tools/factor_priors.py`, в сборку не входит):
−ln P(форма) ≈ −ln P(лемма) − ln P(слот | лемма), слот — пара грамматики,
доля слота общая для всех лемм (181,5 тыс. лемм). Хвосты парадигм снова
общие: словарь 9,0 → 7,4 МБ, но опечатки 77,1 → 76,3% top-1 (ошибка частоты
0,4 ната по употреблению). Исключения (точная частота там, где разложение
ошибается больше чем на 0,3–1,0 ната) возвращают точность (77,1%), но ломают
хвосты своих парадигм: 9,3–10,3 МБ — больше, чем без разложения. Жадный
выбор по длине описания (исключение, где разложение дороже всего
обходится тексту — употреблений × ошибка) лучше: 10 тыс. исключений снимают
73% потерь (7,5 МБ, 76,3%), 30 тыс. — 83% (7,7 МБ, 76,6%), 100 тыс. — 91%
(8,3 МБ, 76,8%). На предложениях (`tools/eval_typing.py`) 30 тыс. исключений —
95,2% слов против 95,5% с точными частотами. В сборке — точные.

Двухуровневая схема (на будущее): автомат только слов, выдающий номер слова
(номер — сумма размеров пропущенных поддеревьев, она зависит лишь от формы
поддерева, так что хвосты по-прежнему общие) — 3,2 МБ; частоты и грамматика —
отдельным массивом по номеру. Энтропия: частота — 1,83 бита на слово (почти
все формы редкие и с одним значением), грамматика — 6,7 бита, но 1,2 бита при
известных 3 последних буквах; граница для массива ~1,3 МБ, итого ~4,5–5,5 МБ
против 9,0. Цена: поиск и дополнение сейчас отсекают по нижней границе
частоты в поддереве (выходы FST), в такой схеме её нет — нужна своя.

### Темп пальца вдоль свайпа (`crates/core/src/gesture.rs`, `Pace`)

Время каждой точки пути: для каждой из 40 точек (по длине) — сколько времени
палец провёл на отрезке вокруг неё, на единицу длины, относительно медианы
жеста. Остановка (локальный максимум, вдвое медленнее обычного) между двумя
буквами слова, которую ни одна не объясняет (дальше 2 точек от обеих), стоит
`ln(медленность/2)`; буква в месте, где палец пролетел (в 0,6 от обычного
темпа и быстрее), — `ln(0,6/медленность)`; обе ≤ 1,5 и только растут, так что
граница перебора остаётся верной. Вес `gesture_pace` = 1, выключается
настройкой. Симулятор (`PACE=corners`: палец тормозит только на поворотах,
буквы на прямой проходит с разгона — худший случай для этой модели) даёт
+1,8…3,2 пункта top-1; `PACE=letters` (тормозит на каждой букве) — +2,7…3,8.

### Эмодзи и буфер обмена (`crates/android/src/panel.rs`)

Долгое нажатие на запятую открывает панель вместо букв: вкладки в полосе
подсказок (📋, недавние, 9 групп Unicode), страница 8×4 поверх трёх рядов,
нижний ряд — АБВ, ‹, пробел (номер страницы), ›, ⌫, ⏎; свайп вбок листает, с
последней страницы группы — в следующую. Список (Unicode emoji-test.txt 17.0
без оттенков кожи, `tools/emoji.py` → `emoji.txt`, 19 КБ) вшит в библиотеку и
разбирается при первом открытии; эмодзи новее шрифта телефона (по
`SDK_INT`) не показываются; рисуется только видимая страница — системным
шрифтом через `Canvas.drawText`. ⌫ стирает эмодзи целиком (ZWJ-склейки,
флаги, модификаторы), а удаление в Java идёт в кодовых точках
(`deleteSurroundingTextInCodePoints`), как считает Rust.

Буфер: Java слушает `OnPrimaryClipChangedListener` и отдаёт текст в Rust;
помеченное приложением как чувствительное (`EXTRA_IS_SENSITIVE`, пароли) не
хранится и не предлагается. Только что скопированное 90 с предлагается в
левой ячейке полосы («📋 …», нажатие вставляет), пока не начат набор; до 12
последних копий — во вкладке 📋 (✕ убирает). Всё — только в памяти, до
перезапуска клавиатуры; выключается настройкой.

### Один путь: место, ввод, поиск (`crates/core/src/engine/context.rs`, `decode.rs`)

Что сказано до слова, читается один раз на место — `Context`: предыдущее
слово (пары слов, его рамка и класс), фраза до управляющего слова
(согласование, управление, подлежащее), предложение (классы смысла). Что
дал палец — `Evidence`: нажатия с их касаниями, начало слова, путь свайпа с
временами или ничего. Одна функция `decode(место, ввод)` — для исправления,
дописывания, свайпа, предсказания, перечитывания слова в тексте, окна из двух
слов и вариантов по свайпу вверх: одно слово на одном месте весит одинаково,
как бы оно ни пришло. Раньше пары, грамматика и тема применялись в пяти
местах IME по отдельности, ещё три брали только пары, предсказание — без
темы, а превью свайпа читало тему без набираемого слова.

Контекст — внутри поиска. Словарь и пары предыдущего слова в модели
контекста обходятся вместе по тем же буквам; у каждого префикса — нижняя
граница цены на этом месте, `w_lm·(−ln(λ·e^(−пары) + (1−λ)·e^(fit_max −
своя))) − бонус_max` (fit_max — наибольшее, что дают классы или окончания
двух слов, бонус_max — фраза и тема), а слово, которое может попасть в
лучшие, получает точную цену той же функцией, что взвешивает готовые слова
(тест: цены совпадают). Так слово, которое место делает вероятным, не
отсекается за редкость: «ко…» после «рыжий» — «кот», хотя сам по себе «ком»
частотнее и поиск оставляет одно слово. Свайп: обход жеста идёт так же, и все
найденные слова (до 60, а не 8) взвешиваются местом до отбора лучших.
Дописывание — A*: по нижней границе вниз, найденное слово возвращается в
очередь с точной ценой, так что первые k вышедших — точно лучшие k на этом
месте (отдельный поиск «слов, которые ждёт предыдущее» больше не нужен).
Без контекста (пустое место) всё вырождается в прежний поиск. Цена
набранного настоящего слова нужна для решения, заменять ли его; если поиск на
этом месте вытеснил его более вероятными словами, она берётся из обычного
чтения, взвешенного тем же местом (то же число) — иначе как раз там, где
контекст сильнее всего против слова, замена была невозможна (набор с шумом
93,15 → 93,31%).

Замеры (`tools/eval_phrase.py`, 600 отложенных предложений): свайп σ = 0,3 —
95,33% слов (было 95,29–95,37%); набор с шумом 0,4 — 93,31% (было 93,39%, в
пределах шума трёх прогонов), аккуратный набор — 0 изменений; следующее слово
— top-1 8,4 / 17,1% там, где грамматика говорит, и в остальных местах (было
8,8 / 17,2%: кандидаты теперь весят смесь пар с частотой, как любое слово).
Классы смысла в предсказании мешали (16,1% при весе 0,5) — `w_topic` = 0,25,
одно значение для исправления, свайпа и предсказания. Цена — задержка: 1–2,3
мс на запрос на ПК вместо 0,8–1,4.

Слова поля помнят, что дал палец (`Input`: буквы с касаниями или путь с
временами): свайпнутое слово перечитывается в тексте, в окне из двух слов и
по свайпу вверх по своему пути, а не как будто его буквы напечатаны.

Подлежащее и сказуемое — выученные веса (`tools/build_frames.py`, `@attr`):
после подлежащего (личное местоимение или существительное только в
именительном, через наречия и частицы — «девочка быстро не…») сказуемое
(глагол, краткое прилагательное или причастие: «она рада») согласуется в
99,5% случаев, случайное — в 37%: +0,99 нат согласованному, −4,87
несогласованному; однородные подлежащие («Эстелла и я идём») читаются
вместе — множественное число, меньшее лицо, а если второе слово словарю не
известно, подлежащего нет, с весом `w_subject` = 1 (между подлежащим и глаголом пары
слов подлежащего не видят). Настоящее слово, против которого грамматика, а за
его другую форму (пропущенная или лишняя буква на конце: «побежал» →
«побежала», «могут выдержат» → «выдержать») — на 2,5 нат, заменяется, если та
всё ещё ясно вероятнее.

Зоны клавиш следуют тексту, но только в тупике: нажатие почти на границе
двух клавиш (цена касания соседа не больше чем на 0,25 выше своей) читается
как соседняя буква, если с нажатой буквой не начинается ни одно слово, а с
соседней начинается (из нескольких — вероятнейшая на этом месте). Выбирать
букву по лучшему слову, которое начинают буквы до неё, нельзя: у короткого
начала лучшее — частое короткое слово («с», «в»), и такие зоны переписали 7
верных слов из 3200 при аккуратном наборе («четко» → «сетко»); букву, с которой
слово идёт дальше, взвешивает исправление всего слова. Это расчёт, не
обучение; после ⌫ набранная заново буква остаётся как нажата. Польза —
дописывания: они ищутся по точному началу слова.

### После свайпа и у курсора

Нарисованное слово сразу уходит в текст с пробелом (следующее начинается
после него; пробел, нажатый следом, не удваивается, знак препинания встаёт на
его место: «слово, »). Другие прочтения пути остаются в полосе — касание
ставит прочтение на место слова тем же путём, что и свайп вверх по пробелу;
⌫ сразу после снимает слово с пробелом целиком (оно было прочитано, не
набрано). Если путь, кроме самого слова, ничего не читает, варианты для
свайпа вверх — прочтения его букв, как будто набранных.

Буква, набранная у конца слова, к которому вернули курсор (перед курсором
буквы, после — не буква), продолжает его: слово подхватывается целиком, и
исправление читает «клев…», а не «ев…». В середине слова буква только
вставляется.

### Окно из двух слов

После пробела предыдущее слово хранит 5 лучших прочтений (с учётом слова перед
ним). Когда текущее слово читается как слово, каждое прочтение `p` получает
`cost(p) + cost(текущее | p)`; если другое прочтение дешевле набранного на
`WINDOW_MARGIN` = 1,5 — в центре полосы «↶ в принципе», пробел ставит оба слова,
⌫ сразу после возвращает оба как были. Слово, которое пользователь правил (⌫,
возврат, повтор после отмены), не перечитывается.

### Калибровка хвата (`crates/android/src/grip.rs`)

По кнопке в настройках, в собственном тестовом поле: дуга левым и правым
большим пальцем (путь + наклон в каждой точке → окружность досягаемости и
связь крена с положением пальца), затем панграмма («в чащах юга жил бы цитрус…»,
все буквы кроме ё и ъ) левой, правой и двумя руками. Нажатия сопоставляются с
буквами фразы динамикой (лишнее нажатие не ломает остальные), смещение от
центра клавиши описывается аффинным полем на хват (`du = a₀ + a₁u + a₂v`: ряды
выше — ниже попадание, дальние клавиши недотягиваются). При наборе хват
угадывается по наклону (акселерометр, только пока клавиатура на экране) и по
нажатиям (одновременные касания и быстрые переходы через всю клавиатуру — две
руки); касание сдвигается на ожидаемое смещение смеси хватов. Хранится в
`grip.conf`: наклоны и коэффициенты, без текста. Вне калибровки ничему не
учится.
